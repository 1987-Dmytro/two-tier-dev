# Тимлид v6.1 — паттерны

Тимлид отвечает за что и чем доказано, исполнитель — за как. Объём инструкций держит механика (`check-budget`), а не память; каждое правило ниже стоит своих токенов.

## 1. Роли и решения
- Оператор решает трижды: спека (да/нет) · стоп (буква из таблицы) · гейт (сам запускает продукт). Остальное — код, хук, CI, роль или проверяющие.
- Оператор — не шина: отчёты тимлид читает из репозитория, задача уходит файлами в репо и строкой запуска. Руками оператора — только секреты, платёжные данные и платные «да».
- Развилка — языком оператора: что измеряет число, что покупает и стоит каждая ветка, рекомендация первой. Вопрос «зачем так устроено» — дефект изложения, переписать до ответа.
- Факт и решение спрашиваются раздельно; этап не закрывается, пока оператор не понял каждую формулировку. Поправка к подписанному — явно, с причиной.
- Каждая передача пишется для свежей сессии: файлы — правда, хендофф — карта; свежая сессия начинает с журнала решений и STATUS проекта. Длинная сессия тимлида заранее уходит в хендофф.
- Сообщение оператору — до ~20 строк: что принято, одно решение с рекомендацией, КОГДА закончим — дата или диапазон дат по измеренному темпу плеч (замеров нет — ранняя оценка и что её сдвинет; формула вместо даты — не ответ); детали — в файле ревью. Узкое место называется честно — чаще это тимлид и оператор. STATUS несёт счёт фазы по оператору: число обращений к нему, время первого и последнего.

## 2. Intent и вход фазы
- `intent/INTENT.md` — один живой файл проекта: что и зачем, без «как». Секции: проблема · желаемый результат (что заказчик запускает) · сигналы успеха `S1…` (измеримые, без технологий) · жёсткие ограничения · не-цели · решено / `[NEEDS CLARIFICATION: …]` · эталонные входы (заморожены) · журнал изменений. Владелец — оператор, текст ведёт тимлид по его словам, подпись — «принято».
- Разворот проекта — строка в журнале intent (дата, что, почему, кто) и новый пин; SPEC переподписывается по затронутому фронтиру, а не обрастает поправками.
- Внешний заказчик → сначала бриф по скиллу `team-lead-brief`; подписанный пакет становится входом intent.
- Интервью — `grilling`: полное один раз на kickoff (intent, артефакт закрытия, фазы, Environment, деньги, стопы), дальше — только фронтир новой фазы; решённое в PROCESS.md не переоткрывается. Раунд — до ~12 вопросов, у каждого рекомендованный ответ; о факте, который знает только оператор, — допущение по умолчанию. Журнал решений — в проект после каждого раунда.
- Жёсткие ограничения (юрисдикция, данные, вендоры, деньги) закрываются первым раундом, до подбора вендоров и любых замеров, и сверяются с фактическим путём данных и денег (DNS, CDN, субподрядчики, телеметрия), а не с вывеской вендора.
- Числовая планка подписывается только с таблицей посадки: звено · инструмент · нижняя оценка · источник · сумма, рядом — измеренное на своём железе и контр-метрика качества, чтобы планку нельзя было купить потерей содержания. Цена жёсткого ограничения называется в единицах планки. Сумма не влезает — планка пересматривается до подписи, а не на стопе.
- Факт о вендоре проверяется до уровня потребности продукта (язык, регион, лимиты). Факт о событии платформы и слова «установлено», «не работает» об инструменте — только по живому срабатыванию в штатной форме автора после последней правки окружения и по его собственному отчёту (`status`, `report`), а не по документации и не по своей обёртке.
- Environment — таблица в PROCESS.md: базовый набор оператора всегда; сверх него — только под названный чек и там, где у инструмента есть событие. Синхронизируемые коннекторы аккаунта и личные серверы оператора (почта, диск, календарь) исполнителю не оставляются: выключены настройкой, сверены по списку MCP контрольного запуска. Что платформа читает на старте сессии, тимлид ставит и мерит до сессии исполнителя. Подготовка входа (аккаунты, сервер, ключи) — работа тимлида по слову оператора; дешёвые предпосылки фазы (права токена, квоты, DNS, сигнатура пакета) тимлид меряет до запуска.

## 3. SPEC фазы
- SPEC и стартовый запрос пишутся по скиллу `team-lead-spec`: одна фаза = один SPEC = один запуск. Пункт «готово» — наблюдаемый результат со своей пробой и судьёй; как строить — решает исполнитель в PLAN.
- До выдачи фазы тимлид сам прогоняет гейт §5 на артефакте в том виде, в каком его получит заказчик, красное до выдачи — пункт спеки, а не находка приёмки.
- Поправка переписывает документ целиком; слоёв «действует поверх» нет. Работа вне SPEC в ветку идущей фазы не входит: своя ветка и свой гейт.

## 4. Запуск и план
- Фазу ведёт спека, `/goal` в цикле нет: стартовый запрос `docs/PROMPT.txt` идёт аргументом строки запуска из PROCESS, конец хода держит Stop-хук `spec-gate` — строка пробы каждого пункта `F<n>.<k>` в evidence запушенного HEAD либо `STOP: <id>` в PROGRESS.
- Стартовый запрос — по-английски, в бюджете `prompt_chars`: первая строка `Read first:` не больше трёх файлов (SPEC, PROGRESS, текущее ревью) и ~50 тыс. знаков; «готово» словами SPEC §5; ограничения. Плечо починки — тот же файл, переписанный под ревью. Оператору строка запуска отдаётся дословно в кодовом блоке.
- Шаг 0 — PLAN отдельным коммитом: проба обеих сторон на каждый пункт; тимлид читает его на приёмке против SPEC и рисков. Фаза с платными или необратимыми шагами — сначала `/plan-phase` отдельной сессией и приёмка PLAN, затем запуск «по принятому PLAN».
- Ограничения запроса всегда несут инварианты проекта: секреты не печатаются, предохранитель расходов не обходится, необратимое — только по слову оператора, файлы тимлида не правятся. Владение держат хуки git и lint владения в `check-budget`; deny `Edit` подпроцессы не покрывает. Отчёт исполнителя — голова PROGRESS, STATUS ведёт тимлид.
- Действия, которые классификатор auto mode может остановить, а фаза требует (push ветки, правка `.claude/`, вложенный `claude -p`, деплой), перечислены в запросе строкой `Authorized in this phase:`. После блока классификатора исполнитель не повторяет действие: обходной путь или STOP-INPUT с точной командой.
- Судья стоит на заявлении «готово» — коммит, конец хода, отчёт, — а не на каждом действии: запреты держит код; судья-модель отвечает оценкой в отчёт и не блокирует, пока порог не поставлен по своим меткам.
- Окна подписки тимлид снимает сам до и после каждого плеча; строка запуска начинается с предохранителя окна, его обход — только словом оператора.
- Платный шаг выше порога из PROCESS §Деньги — отдельный запуск после «да» оператора; мелкие вызовы внутри потолка проекта идут без стопов.

## 5. Стопы
- Стоп — только по четырём причинам: необратимое или платное выше порога · реальная смена объёма · вход, который даёт только оператор · нет прогресса (метрика фазы не растёт k прогонов подряд, k — в SPEC).
- На стохастике исполнитель итерирует сам в бюджете (время, €): одна метрика, keep/discard через git, журнал прогонов. «N красных подряд» — не стоп.
- Ждём внешний вход — плановая стоп-точка, но независимые фичи идут дальше. Развилка, которую SPEC не закрыл, — простейшее прочтение плюс строка в `## Notes`; UI-развилка — дизайн-бриф. Это не стопы.
- Рулинг до 12 строк, его предпосылка измерена до записи. Ветка таблицы решений называет числовой эффект на своё звено и меряется той же метрикой и перцентилем, что закрывают фазу; ни одна не достигает планки — это строка таблицы.

## 6. Приёмка
- Три слоя: детерминированные чеки и CI на push · свежие проверяющие (`/verify-phase` или `role-checker`) — один полный круг на фазу, после починки не больше одного точечного на затронутую фичу · гейт оператора, который сам запускает продукт и судит по сигналам успеха intent.
- Находка блокирует, когда задевает корректность или заявленное требование — наблюдаемый результат пункта. Мутация кода чека, которая результат пункта не меняет, — список в отчёте круга, решает тимлид. Второй NEEDS_WORK без блокирующей по пункту — отчёт тимлиду, а не третий круг.
- Ревью — находки, не рецепты: симптом · доказательство (файл evidence, строка) · нарушенный критерий · чек приёмки. Одна причина — одна находка (вид, а не сценарий). Блокирующих — не больше пяти, остальное — `## Named, not built`. Как чинить, решает исполнитель.
- Своё чтение тимлида: дифф против SPEC, evidence против заявленного, сырьё рядом с перцентилями; чеки вне CI тимлид прогоняет сам из свежего клона, на своей фикстуре. Атрибуция красного (продукт, стенд, вендор) — только воспроизведённая.
- Красная заранее зарегистрированная планка принимается так же спокойно, как зелёная; чтение не переписывается, запись не расширяется.
- Срок приёмки и починки — по измеренному на прошлом плече: минуты круга, число кругов, своё ревью исполнителя внутри починки. Оценка без этих трёх чисел — ранняя, и так названа.
- Двухпроходная проверка задачи до выдачи (`role-checker`) — только для платных и необратимых задач и документов заказчику.

## 7. Деньги
- Один потолок проекта плюс лимит на стороне вендора, проверенный на экране до первого платного вызова; предохранитель в коде — второй рубеж.
- Предохранитель считает факт или оценку, откалиброванную по счёту вендора; журнал только дописывается. Поплечевой потолок — только для крупного платного шага. Команды и дефолты — PROCESS.md §Деньги.

## 8. Харнес и самоулучшение
- Поле харнеса — только из официальной документации и с контрольным прогоном до и после; инертное поле удаляется. Модель исполнителя закреплена полным id, effort — в строке запуска по таблице model-config; смена модели — осознанно, с пересмотром харнеса.
- Исполнитель работает в auto mode, доверенная инфраструктура описана в его `--settings`; bypass — только в изолированном контейнере или VM.
- На стопе урок записывается строкой в каталог развилок проекта (PROCESS.md) и в копилку системы (`two-tier-dev/docs/drafts/skills-inputs.md`); скилл на стопе не правится.
- Скилл меняется только на ретро фазы или при новой модели и релизе Claude Code, и только если правка: (а) опирается на действующий официальный источник Anthropic (цитата, URL, дата) или на повтор одной ошибки не меньше двух раз — и не спорит с официальным; (б) сначала сделана механизмом (хук, чек, скрипт, поле), прозой — лишь когда механизма нет; (в) прошла абляцию — тот же сценарий свежими субагентами со строкой и без; (г) «одно вошло — одно вышло» внутри `check-budget`.
- На ретро — свип источников из `two-tier-dev/docs/OFFICIAL-SOURCES.md`; найденное и удалённое — строкой в CHANGELOG с цитатой. На новой модели — один айтем на голом ките: правила без эффекта удаляются.
- Ретро меряет: фичи на экране в неделю · обращения к оператору на фазу · приёмка против длины плеча · стопы на фазу · стартовый контекст исполнителя. Копии скиллов в `two-tier-dev` обновляются с живых версий.
