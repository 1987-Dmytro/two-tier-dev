# Наша система разработки с ИИ-агентами — двухуровневый цикл «оператор · тимлид · исполнитель»

**v2.0 · 18.09.2026** (v1.1 — 06.09, целиком в `docs/archive/`). Выведена из практики: одна фаза проекта-источника (сентябрь 2026) — 29 сессий исполнителя, 25 рулингов, девять разборов остановок; пересобрана 18.09 по решениям D1–D17 и архитектуре `docs/two-tier-dev-v2-architecture.md`. Живёт не в генераторе, а в ките: папка `kit/`, которую `bin/two-tier-init` копирует в любой репозиторий, плюс два скилла тимлида. Этот файл — описание системы целиком, чтобы её можно было применить к следующему проекту и передать стороннему человеку.

## 0. Одним абзацем

Один человек — **оператор** — ведёт разработку через два яруса ИИ: **тимлида** в Cowork (Fable 5.1, скиллы `team-lead` и `grilling`) и **исполнителя** в Claude Code (Opus 5 в ультракоде). Четвёртый актор — **evaluator** (Haiku, без Write и Edit): отдельный проход приёмки, запускаемый не исполнителем, а командой `/accept`. Цепочка одной фазы: `intent/<slug>.md` → прожарка → `docs/SPEC-<n>.md` → plan mode → `docs/PLAN-<n>.md` коммитом → один `/goal` → `docs/PROGRESS.md` и `docs/evidence/` → `/accept` → `docs/STATUS.md` → гейт. Оператор принимает ровно **три решения**: спека да/нет · буква на стоп-точке · гейт (сам открывает продукт). Система оптимизирует не скорость написания кода, а **стоимость проверки**: верификация обязана оставаться дешевле сборки, а истина считается **продуктовой** (оператор своими руками запускает артефакт закрытия), не процессной (зелёные тесты ничего не закрывают).

## 1. Три роли, четвёртый актор — и что никогда не делегируется

| роль | где | владеет | никогда не делает |
|---|---|---|---|
| **Оператор** | Cowork + Claude Code | цель, метрика, деньги, понимание системы; `intent/<slug>.md` при внешнем входе; три решения — спека · буква на стоп-точке · гейт | не пересказывает отчёты между приложениями, не пишет PLAN, не ревьюит диф руками, не отвечает на вопрос, который SPEC мог закрыть заранее (это дефект SPEC, а не оператора) |
| **Тимлид** | Cowork, папка репо привязана; Fable 5.1 | прожарка по `grilling`, `docs/SPEC-<n>.md` шести секций, `docs/PROCESS.md`, чтение STATUS и evidence, рулинги в `docs/reviews/`, ретро фазы | не пишет шаги реализации (их строит исполнитель в PLAN), не пишет продуктовый код, не принимает работу по прозе — только по файлам `docs/evidence/*-result.txt` |
| **Исполнитель** | Claude Code, Opus 5 в ультракоде; свежая сессия на фазу | PLAN, код, чеки и их evidence, коммиты по путям, `docs/PROGRESS.md`, дельта Environment | не правит SPEC · PLAN · STATUS · PROCESS · `docs/reviews/` · `docs/archive/` · `intent/` (`permissions.deny`), не проверяет себя сабагентами, не принимает свою работу |
| **Evaluator** | Claude Code, сабагент из `/accept`; Haiku, без Write и Edit | вердикт `PASS` / `NEEDS_WORK` по `REVIEW.md`: диф против SPEC и PLAN, каждый файл evidence открыт и прочитан | не вызывается исполнителем для самопроверки, не чинит найденное, не выносит вкусовых находок (лестница Ponytail, уровень `full`) |

**Не делегируется ничего из трёх решений оператора** — и только они: всё остальное обязано быть кодом, хуком или вердиктом evaluator'а. Карта, документы и разговор — на языке оператора.

## 2. Два скилла и граница между ними

**`team-lead` v4 (сторона Cowork).** ≤80 строк, **только паттерны**: роли и три точки решения · вход фазы и прожарка · SPEC шести секций · `/goal` · приёмка · стоп-точки и рулинги · деньги · harness и рост закона. Единица версионирования — больше не карточка: то, чему система научилась, живёт в `CHANGELOG.md` репо, а сюда правило доходит последним (§7). Карточки v1 — v3.20 и v3.23 — лежат в `docs/archive/`.

**`grilling` (сторона Cowork).** Копия скилла Мэтта Покока (MIT) с лицензионной строкой: дерево дизайна вместо интервью по памяти — раунды по открытому фронтиру, нумерованные вопросы с рекомендуемым ответом, факты добывает ассистент, решения принимает оператор, конец — пустой фронтир. Полная прожарка — один раз на kickoff; каждая следующая фаза прожаривает только свой фронтир.

**`brain-init` больше нет.** Его работу делают примитивы, которые не надо сопровождать: пять хуков `anthropics/cwc-long-running-agents` (Apache-2.0, verbatim) и `agents/evaluator.md`, два наших `PreToolUse(Bash)` (`refuse_sweeping_commands.py` из v1 и фильтр тестового вывода) и два скилла исполнителя — `plan-phase` (шаг 0 фазы) и `accept` (приёмка), оба с `disable-model-invocation: true`. Генератор заменён копированием: `bin/two-tier-init`. Сам v1-набор — в `docs/archive/brain-init-v1/` и `docs/archive/executor-kit-v1/`.

**Граница — главное правило системы.** Паттерн → скилл. Механика проекта (команды, флаги, цены, пути, платформа) → `docs/PROCESS.md`. Правила фазы → `docs/SPEC-<n>.md`. Шаги реализации → `docs/PLAN-<n>.md`. Решения по ходу → рулинг в `docs/reviews/`. Детерминированное правило → хук, до всякого текста. Дефолты шаблонов → `kit/docs/*.template.md`. Тест для строки скилла: **прочитается ли она так же в проекте на другой платформе, в другой валюте, с другим исполнителем?** Если нет — она принадлежит проекту, а в скилл идёт только её паттерн.

## 3. Артефакты и потолки

| файл | пишет | потолок | что это |
|---|---|---|---|
| `intent/<slug>.md` | оператор | — | проблема · желаемый результат (что ЗАПУСКАЕТСЯ и что видно на экране) · пользователи и системы · ограничения · открытые вопросы. Обязателен при внешнем входе; своя идея — десятистрочная шапка SPEC |
| `docs/SPEC-<n>.md` | тимлид | шесть секций | 0 Контекст · 1 Дизайн высокого уровня (без деталей реализации) · 2 Фичи строкой `id · user story · «готово» · команда чека · after: · [P]` · 3 Инварианты и границы · 4 Стоп-точки · 5 Артефакт закрытия · 6 Открытые вопросы |
| `docs/PLAN-<n>.md` | исполнитель | четыре раздела | файлы · порядок · риски · доказательство; пишется в plan mode шагом 0 и коммитится до первой правки кода; критерий — по нему реализует инженер, не видевший разговора; отклонение → правка PLAN тем же коммитом |
| `docs/PROGRESS.md` | исполнитель | 60 строк | память фазы: сделано (коммит + маркер чека) · ОДИН следующий айтем · `STOP: <id>` с постоянной строкой resume · `Notes` · «названо, не построено» |
| `docs/STATUS.md` | `/accept` (Write целиком; `Edit` запрещён правилом `deny`) | 60 строк | карта оператора: где мы, **когда закончим**, дата гейта, строка запуска продукта |
| `docs/PROCESS.md` | тимлид | — | механика проекта: **Environment** таблицей (инструмент · форма · требующая фича/чек · установка · удаление) · **Деньги** (восемь дефолтов) · **каталог развилок** с классами стопов |
| `docs/evidence/<fid>-<check>-result.txt` | исполнитель | — | вывод каждого чека на диске: в ультракоде промежуточные результаты воркфлоу живут в переменных скрипта, а не в транскрипте, поэтому доказательство обязано лечь в файл; маска `*-result.txt` — та, что засчитывает `track-read.sh` и требует `verify-gate.sh` |
| `docs/reviews/<дата>-*.md` | тимлид | ≤12 строк на рулинг | журнал решений: рулинг решает (выбор · число из инструмента · файл), никогда не законодательствует |
| `CLAUDE.md` проекта | оператор при развёртывании | ≤40 строк | закон исполнителя на каждую свежую сессию: факты проекта, правило evidence, рамки задачи, стоп-точки, указатель на `REVIEW.md` |
| `REVIEW.md` | — (едет китом, правится осознанно) | — | по чему evaluator выносит вердикт: баги · безопасность · соответствие SPEC и PLAN · что считать Important |
| `/goal` | тимлид, оператору verbatim | ≤4000 символов | одно измеримое конечное состояние + названный чек (команда → вывод) + ограничения + «stop after N turns» + стоп-точка как выполненный goal |

**Фича** = вертикальный срез, который показывают сам по себе и который влезает в **одно свежее окно контекста**. Одна фаза = один SPEC = один `/goal`.

## 4. Цикл

```
ВХОД ФАЗЫ   intent/<slug>.md (оператор) → прожарка по grilling в Cowork: раунды по фронтиру, вопросы с
            рекомендуемым ответом → docs/SPEC-<n>.md (шесть секций) → РЕШЕНИЕ 1: оператор подписывает спеку
               │
ПЛАН        /plan-phase: исполнитель читает SPEC в plan mode → docs/PLAN-<n>.md отдельным коммитом (файлы ·
            порядок · риски · доказательство) + дельта Environment «поставить / убрать» → стоп. Реализацию
            открывает только /goal оператора
               │
РАБОТА      один /goal на фазу → фича за фичей: код → чек своей командой → вывод в транскрипт И в
            docs/evidence/<fid>-<check>-result.txt → коммит по точным путям → строка в PROGRESS
               │
СТОП        `STOP: <id>` в PROGRESS + постоянная строка resume = ВЫПОЛНЕННЫЙ goal, а не отказ →
            РЕШЕНИЕ 2: оператор отвечает буквой из таблицы решений → работа продолжается свежей сессией
               │
ПРИЁМКА     /accept <база фазы>: диф, evidence и STATUS собраны, каждый файл прочитан инструментом Read →
            evaluator по REVIEW.md → PASS: STATUS переписан (когда закончим · дата гейта · строка запуска);
            NEEDS_WORK: находки в PROGRESS «Next», починка — следующий /goal, не эта сессия
               │
ГЕЙТ        РЕШЕНИЕ 3: оператор сам запускает артефакт закрытия и говорит, что это то. Ретро фазы → §6 SPEC
            становится входом следующей фазы
```

**Harness — то, что держит цикл, пока оператора нет за клавиатурой.** Файл `AGENT_STOP` в корне останавливает исполнителя на любом инструменте; строка в `STEER.md` вмешивается на лету; `commit-on-stop.sh` коммитит на Stop и пишет в PROGRESS; `verify-gate.sh` не даёт записать результат теста без прочитанного evidence; `refuse_sweeping_commands.py` ловит подметания (`git add -A`, `rm -rf`); `test-output-filter.sh` режет тестовый шум и оставляет итоговую строку.

**Единица работы** — фича, а не «пункт за сессию»; единица *проверки* — её команда чека с файлом evidence. Никогда не считать, что сессия исполнителя жива: каждая передача пишется для свежей.

## 5. Деньги — паттерны (механика с командами — в `docs/PROCESS.md` проекта, раздел «Деньги»: восемь дефолтов из `kit/docs/PROCESS.template.md`)

- **Один платный ран = одна денежная линия**: своё имя, свой якорь — чтение ВНУТРИ платной сессии, за минуты до создания ресурса, никогда сессией раньше (старый якорь пьёт каплю всегда-включённых ресурсов в ссылку закрытия, и полоса допуска закрывается за часы), кап рана как её кап, закрытие по записи рана в той же сессии. Открытая многорановая линия нового рана не несёт. Регистрация читает гард **своей** линии; дефолтное имя линии в эмиттере — следующий отказ. **Регистрация ≠ открытие линии:** запись (пины, граница, железо, цена, бэкстоп) пишется и читается за $0 — тимлид до покупки читает пробный расчёт и код на HEAD; если эмиттер регистрирует и открывает одной командой, она выполняется в платной сессии, а регистрация читается на приёмке против пробного расчёта. Рулинг и `docs/PROCESS.md` разошлись по механике — прав PROCESS.md: исполнитель идёт по нему, называет противоречие в PROGRESS, не останавливается.
- **Ставка — среднее ЦЕЛОГО рана самого медленного хоста** (n = единицы рана), никогда смок из трёх и никогда заимствованная у сиблинга. Дорогой угол (максимум на каждой единице) считается и показывается; когда он не влезает — нога выпускается на среднем угле с капом как жёстким стопом и без полосного гейта.
- **Кап цитируется из пробного расчёта**, который его назвал, — не печатается из текста опции или старой оценки. Ограда для более позднего шага — оценка, не кап: перерасчёт на регистрации этого шага.
- **Железо и цена — поля записи**, прочитанные с платформы за $0 (оба имени: для создания и для прайса), не константы эмиттера. Бэкстоп платформы выводится из капа по зарегистрированной цене; заимствованная константа минут, кусающая первой, ограничивает чтение, а не деньги.
- **Смок — самый длинный рендер первым**: железо, которому не хватает, падает на трёх единицах, не на восьмидесяти. Раннер пишет ответ-ошибку упавшей единицы и выходит ненулевым; клиент читает её и удаляет ресурс сразу, а не ждёт дедлайн. Новая форма строки ответа читается **всеми** читателями файла в той же починке.
- **Закрытие линии — по её пост-рановому чтению**, снятому после освобождения ресурса и до любого следующего рана (ссылка гейта — последнее открытое чтение; дорановое отказывает навсегда). Линия без такого чтения закрывается по одному биллинговому walk'у в своём окне и позднего чтения не берёт. Биллинг запаздывает — частичный walk отказывается и повторяется в начале следующей сессии.
- **Валидность платного чтения**: ран считается, только когда каждая единица отвечена и распарсена; сервинг-отказ (нехватка памяти, крах) двигает сервинг, не инструмент; перекупка — следующий номер на своей линии.
- **Потолок цикла — слово оператора** по таблице (варианты · что влезает · когда спросят снова); якорь никогда не перегенерируется; всегда включённые ресурсы капают в каждое открытое окно; teardown доказывается листингом. **Гейт ранбука — команда, которая может провалить сессию** и стоит ПЕРЕД шагом, который охраняет; печатный «STOP» с нулевым кодом возврата — заметка, а не гейт.

## 6. Честность и научная дисциплина

Ни одного числа без сида, конфига, происхождения и файла. Претензии **предрегистрируются**: чтения-не-бары там, где оператор решает по таблице; бары с критериями там, где делается заявление; **одна попытка на замороженном наборе**; красный бар закрывает вопрос, под который был зарегистрирован, — и принимается так же спокойно, как зелёный; неполный ран не закрывает ничего и называется неполным. **Инструмент на замороженном наборе — байт-в-байт тот, что взял dev-бар**; косметика закона встаёт в очередь за попыткой. **Сожжённый набор понижается до чтения**, следующий бар нуждается в НОВОМ наборе из **популяции продукта** (источники, которые продукт реально читает), никогда из надмножества. Решение называет **команду**, чей вывод — число, а не число; правило без команды никто не проверяет. Синтетика помечается и никогда не попадает в замороженные наборы; витрины читают `docs/evidence/*-result.txt` и громко падают. Чек, у которого нет файла evidence или нет маркера в файле, не пройден, даже если код на месте.

## 7. Как система учится

Каждая остановка — урок, без исключений: класс (`planned read · fork · defect · money · process · question`) → мог ли ответить SPEC фазы? → какое правило входит и **куда**. **Правило роста закона:** новое правило появляется только при **повторе той же ошибки** без него — и сначала как **hook**, потом строкой в `docs/PROCESS.md` (механика) или дефолтом каталога развилок, и лишь потом паттерном в карточку `team-lead`. Класс, встреченный дважды, становится дефолтом каталога развилок; дефолт, не выстреливший за фазу, удаляется на ретро. Находка верификатора **до** покупки — остановка, которой не случилось: проходит тот же разбор. **Метрики ретро с порогами диеты:** строки верификации ÷ строки продукта > 3 · процессные коммиты > 25 % · остановок > 1 в день · артефакт над потолком · предвидимых остановок > 0 — пересечение любого = следующая сессия не фича, а диета, и диета может означать, что растут дефолты SPEC и PROCESS.md, а не закон исполнителя. Три денежных остановки за день = в шаблоне PROCESS нет раздела «Деньги» — пишутся его дефолты разом, не по правилу на остановку.

Честный счёт трёх дней v1: 04.09 — 8 сессий, 4 остановки; 05.09 — 8 сессий, 7 остановок, из них 4 предвидимые и все — денежные промахи тимлида; 06.09 — 1 сессия, 1 остановка, снова денежная: рулинг разошёлся со стоящим PROCESS.md по тому, КОГДА берётся якорь линии. Ответом стали не новые правила по одному, а дефолты — раздел «Деньги», шаблон файла фазы (`docs/archive/templates-v1/PHASE.md`), карточка скилла. Слабое место системы — денежная механика при смене железа и линий; сильное — ни одного доллара не потеряно без имени и ни одного числа, взятого из прозы.

## 8. Где что живёт

- **Репо `two-tier-dev`** — канонический экземпляр системы: `kit/` (22 файла, которые уезжают в каждый проект), `bin/two-tier-init`, `docs/` (этот файл, `SPEC-v2.md`, `PLAN-v2.md`, архитектура, `evidence/`), `CHANGELOG.md` — чему научилась каждая версия и какая остановка её научила.
- **`docs/archive/`** — вся v1 целиком, ни один файл не удалён: карточки тимлида v3.20 и v3.23, `executor-kit-v1/`, `templates-v1/`, `brain-init-v1/`, `new-project.sh`. Читается как история, не как инструкция.
- **Машина оператора, `Projects/<проект>/`** — кит развёрнут в корень: `CLAUDE.md`, `REVIEW.md`, `.claude/` (settings.json, пять хуков cwc + два наших, `agents/evaluator.md`, `rules/graphify.md`, четыре скилла), `docs/` из шаблонов, `intent/`.
- **Cowork-сессия тимлида** — папка репо привязана read/write; git только `git --no-optional-locks …` (обычный `git status` оставляет lock, который VM не может удалить); файлы тимлида правятся на монтировании и **коммитятся исполнителем по пути**.
- **Аккаунт Claude** — карточка скилла тимлида в списке скиллов Cowork-сессии; версия v4 репозитория лежит в ките, живая карточка Cowork из содержимого репо не производится.
- **Внешние источники, взятые как есть:** `anthropics/cwc-long-running-agents` (Apache-2.0) — пять хуков и `evaluator.md`; `mattpocock/skills` — `grilling` (MIT). Копии лежат в ките с лицензионной шапкой и правятся только осознанно.

## 10. Как запустить новый проект по этой системе

1. `cd <проект> && bin/two-tier-init . && claude` — кит ложится в корень целевого репо; существующие файлы не перезаписываются.
2. Заполнить `CLAUDE.md` (стек, команда запуска, команда чека) и `docs/PROCESS.md` из `kit/docs/*.template.md`: Environment, Деньги, каталог развилок.
3. Kickoff-инструменты — ставятся только под названный чек или фичу: **Context7** как MCP (доки библиотек); **graphify** — `pip install graphifyy && graphify install`, затем `/graphify src --wiki` и `graphify hook install` (post-commit, AST, без LLM), MCP-режим выключен; **ponytail** — `/plugin marketplace add DietrichGebert/ponytail`, затем `/plugin install ponytail@ponytail` (ДВА отдельных сообщения), уровень `full`.
4. Оператор пишет `intent/<slug>.md`; тимлид в Cowork — `/team-lead` и **полная прожарка по `grilling` один раз на kickoff** (контекст · артефакт закрытия · фичи · чеки · Environment · деньги · стоп-точки) → `docs/SPEC-1.md` → подпись оператора.
5. Исполнитель: `/plan-phase 1` → `docs/PLAN-1.md` коммитом → один `/goal` на фазу → evidence и PROGRESS → `/accept` → STATUS. Гейт: оператор сам запускает артефакт закрытия. Каждая следующая фаза прожаривает только тот фронтир, который открыла предыдущая (§6 её SPEC).
