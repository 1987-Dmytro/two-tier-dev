**v3.3 · 10.10.2026 — судья на заявлении: коммит судят код и `abide check`, конец хода — `spec-gate` по пунктам спеки, плечо — отчёт фазы и один круг `/verify-phase`.** Как собран v3.3 — `docs/SPEC-v3.3.md` и `docs/PLAN-v3.3.md`. v3.2 (09.10, без `/goal`, Jev-слой) — `docs/SPEC-v3.2.md`; v3.1 (07.10, ultracode по полной) — `docs/SPEC-v3.1.md` и `docs/PLAN-v3.1.md`; v3.0 (06.10) — `docs/SPEC-v3.md` и `docs/PLAN-v3.md`; v2 (18.09) — в истории git этого файла, кит v2 — в `docs/archive/kit-v2/`. Зачем — `intent/INTENT.md` (D5–D7, S8).

## 0. Одним абзацем
Оператор ведёт любой проект циклом **intent → прожарка → SPEC → запуск фазы → приёмка → гейт** — без `/goal`: фазу запускает стартовый запрос в строке запуска, а строка начинается с предохранителя окна подписки `bin/check-window`. Тимлид (Cowork) задаёт результат, проверку, границы и стопы; исполнитель (Claude Code, `claude-opus-5-5`, auto mode, **ultracode** — штатный режим: сам планирует воркфлоу из агентов на каждую существенную задачу) строит путь сам. Судья стоит на заявлении «готово», а не на каждом действии: «кусок готов» — коммит, его судят git-хуки кита и `abide check`; «фаза готова» — конец хода, его держит Stop-хук `spec-gate` по пунктам спеки в запушенном HEAD; «плечо готово» — отчёт фазы, собранный кодом, и один круг `/verify-phase`. Объём инструкций держит механика (`bin/check-budget` в CI), а не память; intent живой и закреплён в SPEC пином; харнес — только по официальной документации, каждое поле проверено контрольным прогоном.

## 1. Роли
| роль | владеет | не делает |
|---|---|---|
| **Оператор** | цель, деньги, три решения: спека да/нет · буква на стопе · гейт (сам запускает продукт); обход предохранителя окна — только его словом | не шина между ярусами: задача уходит файлами в репо — SPEC и стартовый запрос |
| **Тимлид** | `intent/INTENT.md`, `docs/SPEC-<n>.md`, стартовый запрос `docs/PROMPT.txt`, `docs/PROCESS.md`, `docs/STATUS.md`, ревью, `.claude/launch.settings.json`, правила коммита в `CLAUDE.md` и рубрика Abide `.abide/rubric.json`, `.claude/spec-gate.json` | не пишет шаги реализации |
| **Исполнитель** | `docs/PLAN-<n>.md` (проба каждого пункта обеих сторон), код, коммиты по путям с id пунктов, evidence, `docs/PROGRESS.md` (голова — отчёт фазы) | не правит файлы тимлида (deny `Edit`, хук коммита, lint владения), не проверяет себя сам |
| **`/verify-phase`** | вердикт `VERDICT: PASS` / `NEEDS_WORK` по `REVIEW.md` — сохранённый воркфлоу: проверяющие `claude-sonnet-5-5` по фичам со своими фикстурами и мутациями, судья `claude-opus-5-5` | свежий клон и свежий `claude -p` на каждой приёмке, 30 мин; один полный круг на плечо, после починки — точечный |

## 2. Цикл v3.3 — без `/goal`
1. **Intent.** Один живой `intent/INTENT.md` (шаблон `docs/INTENT.template.md`): проблема · результат · сигналы успеха `S1…` · жёсткие ограничения · не-цели · решено и `[NEEDS CLARIFICATION: …]` · эталонные входы · журнал разворотов. Разворот — строка журнала и новый пин, а не поправка поверх SPEC.
2. **Прожарка** по `grilling` — полная на kickoff, дальше только фронтир новой фазы.
3. **SPEC** (шаблон `docs/SPEC.template.md`): шапка `intent/INTENT.md @ <12 знаков hash-object>`; строка фичи — `служит: S…`, чек → маркер; под ней **пункты** `F<n>.<k>` — наблюдаемый результат и место, где он читается (команда, файл, маркер, блок, отказ, вердикт, отчёт); блок фичи — до 900 знаков; таблица судей; у каждой строки §3 — `судья:`; стопов четыре.
4. **Запуск фазы** — строка из `docs/PROCESS.md`: `bin/check-window && … claude --effort ultracode --setting-sources project,local …`, последний аргумент — стартовый запрос `"$(cat docs/PROMPT.txt)"` после `--` (шаблон `docs/PROMPT.template.txt`): до 4000 знаков, `Read first:` — до трёх файлов, «сделано» — строка пробы каждого пункта, один круг `/verify-phase`, отчёт фазы и гейт; стоп — только по SPEC §4, разрешённые действия строкой `Authorized in this phase:`. Ручного набора нет.
5. **Предохранитель окна.** `bin/check-window` одним ходом `claude -p` на Haiku снимает окна подписки и отказывает до старта, когда окно 5 ч выше 40 % или неделя выше 85 %: печатает оба числа и время сброса. Плечо починки и `bin/verify-phase` — флаг `--repair`, порог окна 5 ч 70 %. Числа не сняты — отказ с причиной. Обход — только флагом `--override` в строке, словом оператора; обход печатается. Пороги — ключи `window_five_hour_pct`, `window_seven_day_pct`, `window_repair_pct` в `budgets.json`.
6. **PLAN** — шаг 0 внутри запуска: проба каждого пункта с двумя сторонами (зелёная и красный образец, на котором результат не наступает) · файлы · порядок · риски · отклонения от SPEC по докам. Фаза с платными или необратимыми шагами — сначала `/plan-phase` и приёмка плана.
7. **Работа**: мелкие коммиты, id пункта в начале сообщения (`F2.3: …`), проба — в том же коммите, `git add` по путям; каждая проба печатает строку `F<n>.<k> <сырой вывод>` в `docs/evidence/<F>-<check>-result.txt`, маркер фичи — только после всех её проверок.
8. **Коммит — «кусок готов».** Хук `.githooks/commit-msg` (`core.hooksPath` ставят `bin/two-tier-init` и `bin/two-tier-upgrade`) сначала судит кодом: значение секрета, почта или домашний путь в evidence, файл тимлида без «Тимлид:», удаление мимо `git mv` — отказ с правилом и файлом; затем `abide check` по рубрике тимлида: от 0,8 — отказ один раз, тот же дифф ещё раз проходит как «отклонённый», его читает тимлид; 0,5–0,8 — заметка; ошибка — пропуск. `.githooks/pre-push` отказывает force-push при любом написании. Журнал — `commit-judge.jsonl` в `docs/evidence/`.
9. **Конец хода и стоп — «фаза готова».** Ход кончается, только когда `spec-gate` видит в запушенном HEAD строку пробы каждого пункта, маркер каждой фичи, обновлённую голову PROGRESS и PASS полного круга плюс точечный PASS по фичам, изменённым после него, — или новую строку `STOP: <id>` в запушенном HEAD, с вопросом и resume-строкой. Блок называет id недостающего пункта. Причины стопа: платное или необратимое выше порога · смена объёма · вход оператора · нет прогресса. Развилка, которую SPEC не закрыл, — простейшее прочтение и строка в `## Notes`.
10. **Приёмка — «плечо готово»** — CI на push · отчёт фазы `bin/phase-report` (матрица «пункт × коммиты, проба, наблюдение»; пункты без коммитов, коммиты без пункта, пункты без пробы; счёт судей коммита; пропуски хука; ячейка Jev в тени) · **один круг** `/verify-phase` (`bin/verify-phase`: свежий клон, гейт, по фиче — свежий чек, пограничные случаи против пунктов, мутация; проверяющий подтверждает пункт только своей командой и её сырым выводом; выжившая мутация блокирует; вердикт в `docs/evidence/verify-<sha>.txt`, лимит 30 мин — иначе `VERIFY_TIMEOUT`); его блокирующие исполнитель чинит в той же сессии и перепроверяет только затронутые фичи (`bin/verify-phase F2 …`, строка `FEATURES: F2` в вердикте) — второго полного круга нет · ревью тимлида, до пяти блокирующих находок. STATUS пишет тимлид.
11. **Гейт** — оператор запускает продукт и судит по сигналам intent.

## 3. Бюджеты — механикой
`bin/check-budget` читает `budgets.json` (defaults кита; `project` только ужесточает) и печатает OK/WARN/FAIL на правило и `BUDGET_OK`. Знаки — символы Unicode.

| что | предел |
|---|---|
| копия `team-lead` (`docs/drafts/team-lead-v6.md`) · `team-lead-brief` | 80 строк и 12 000 знаков · 150 строк и 15 000 знаков |
| скилл кита · `CLAUDE.md` кита | 4 000 знаков, без `$` с цифрой · 40 строк |
| `intent/INTENT.md` | 6 000 знаков (WARN); маркер неясности — WARN |
| строка фичи SPEC · блок фичи с пунктами | 600 знаков, `служит:` ссылается на существующий S · 900 знаков (`spec_block_chars`); у пункта — место чтения, у строки §3 — судья; маркер неясности в SPEC — FAIL; пин = hash-object INTENT |
| `docs/PROGRESS.md` · PLAN фазы | 60 · 150 строк |
| стартовый запрос `docs/PROMPT.txt` | 4 000 знаков (`prompt_chars`); `Read first:` — до 3 файлов и 50 000 знаков вместе с CLAUDE.md |
| рубрика Abide `.abide/rubric.json` | до 8 правил (`abide_rules`); красный образец каждого — от 0,8 |
| окна подписки на старте | 5 ч — 40 %, неделя — 85 %, починка — 70 % (`window_five_hour_pct`, `window_seven_day_pct`, `window_repair_pct`) |
| ревью `docs/reviews/*` | блокирующих — до 5 |
| владение | коммит после merge-base с `main`, меняющий файл тимлида, — только «Тимлид:»; список — на родителе коммита, `budgets.json` в нём; стартовый запрос наследует владение прежнего `docs/GOAL.txt` |

CI (`.github/workflows/two-tier.yml`) гоняет `bin/check-budget` и `make ci` на каждый push и PR; `bin/check-ci <ветка>` засчитывает только прогон текущего HEAD.

## 4. Харнес
- `.claude/settings.json`: модель полным id; effort не задан — ultracode и effort фазы в строке запуска; `worktree.baseRef: "head"` (агент в worktree видит HEAD ветки, а не `main`); `workflowSizeGuideline: "medium"`; узкие allow на `bin/check-*`, `bin/gate-*`, `make ci`; `autoMemoryEnabled: false`; `disableClaudeAiConnectors: true`; deny `Edit` на файлы тимлида (Edit покрывает и Write); хуки exec form с `${CLAUDE_PROJECT_DIR}`.
- `AGENT_STOP` в корне — kill-switch: `continue: false` со `stopReason`, вызов не выполняется, прогон останавливается — и у главной сессии, и у агента воркфлоу. Строка в `STEER.md` — заметка фактом в `additionalContext`, только главной сессии (у агента во входе хука `agent_id`).
- Агенты воркфлоу правят только в своих worktree или только читают; коммит — главная сессия; push в `main` запрещён (`kit/CLAUDE.md`, его читает и классификатор auto mode); `main` держит защита ветки GitHub.
- **Окружение = таблица.** Таблица Environment в `docs/PROCESS.md` (инструмент · форма · id · вкл · фича · установка · удаление) → `enabledPlugins` и `skillOverrides` в `.claude/launch.settings.json` и строка запуска: `bin/check-window && … --permission-mode auto --model claude-opus-5-5 --effort ultracode --settings .claude/launch.settings.json --strict-mcp-config --mcp-config …`. Флаги — `docs/LAUNCH.md`. Инструмент стоит там, где есть его событие.
- **Слой Jev** (D6) — у исполнителя только тень: Jev Belay — второй судья конца хода, только журнал; ячейка Jev в отчёте фазы — пункт против сырого вывода его пробы, «подтверждает / противоречит / молчит», не блокирует; мод `handoff` — хендофф на 70 % окна; `bin/jev` — типизированные вопросы Jev обоим ярусам; `bin/check-spend` — расход за плечо. Toolgate, хуки Abide на правку и ход, Compact Adviser и Steer-or-Queue ушли из кита исполнителя (их файлы — `docs/archive/kit-v3.2/claude-config/`): их события — каждое действие и сообщение человека посреди хода — есть только в сессиях оператора. Мод `limits` — статус-строка окон подписки в сессиях оператора.
- `bin/check-harness` — по разделам: `items` — конец хода по пунктам (`ITEMS_OK`, `GATE_HOOK_OK`); `commit` — судьи коммита и рубрика (`COMMIT_OK`); `env` — пара строкой запуска: `system/init` = таблица, ни один хук на действие не ходит в сеть и не зовёт модель (`ENV_OK`), заметка доходит, стоп-кран останавливает, allow-правила работают, `claude doctor` чист (`HARNESS_OK`), deny, отказ широких команд, стоп-кран и заметка — на главной сессии и на агенте воркфлоу (`HOOKS_OK`). Итог «до и после» — в CHANGELOG.

## 4а. Три судьи по цене вопроса — и три заявления
- **Код** — где ответ даёт grep или файл: строка пробы пункта в evidence, ветка запушена, PASS для HEAD, секрет в диффе, force-push. Бесплатно и без ложных срабатываний; запреты держит только код.
- **Jev** — где вопрос ограничен документом и повторяется: у исполнителя — в тени, одна ячейка отчёта фазы и `abide check` коммита по рубрике тимлида (отказ один раз, последнее слово за исполнителем). Метки копятся; выход из тени — по своим меткам, на ретро.
- **Свежий агент** — где нужно воспроизвести или синтезировать: `/verify-phase` (свежий клон, свои фикстуры, мутации, опровергатели, судья). Дорого — один круг на плечо.
Судья на заявлении: «кусок готов» — коммит (код, затем `abide check`), «фаза готова» — конец хода (`spec-gate`), «плечо готово» — отчёт фазы и один круг `/verify-phase`. Между заявлениями модель-судья молчит.

## 5. Самоулучшение
- Правило харнеса, кита или скилла меняется только по `docs/OFFICIAL-SOURCES.md` (цитата, URL, дата) или по повтору одной ошибки не меньше двух раз — и без спора с официальным.
- Сначала механизм (хук, чек, скрипт, поле), проза — лишь когда механизма нет; правка проходит абляцию (тот же сценарий свежими субагентами со строкой и без, `claude/evals-2026-10-06/`); «одно вошло — одно вышло» внутри бюджета.
- На стопе урок — строкой в каталог развилок проекта (`docs/PROCESS.md`), скилл на стопе не правится. Ретро фазы и новая модель — свип источников; найденное и удалённое — строкой в CHANGELOG с цитатой и адресом.

## 6. Где что живёт
Кит — `kit/` (`bin/two-tier-init` кладёт его в корень проекта). Инструменты проекта — `kit/bin/`. Хуки git — `kit/.githooks/`. Шаблоны — `kit/docs/`. Моды — `mods/` (`handoff`, `limits`). Копии скиллов Cowork — `docs/drafts/`. История — `docs/archive/`: ничего не удаляется, выводимое уходит туда `git mv`; гейты прежних фаз — `docs/archive/gate-v3.2/` и раньше.

## 7. Как начать и как перевести
- **Новый проект:** `git init` → `<two-tier-dev>/bin/two-tier-init .` (кит в корне, `core.hooksPath` → `.githooks`) → `bin/check-budget` → `BUDGET_OK`. Тимлид пишет intent, SPEC, стартовый запрос `docs/PROMPT.txt`, `launch.settings.json` и рубрику коммитами «Тимлид:», оператор запускает исполнителя строкой из `docs/PROCESS.md` — она начинается с `bin/check-window && ` (флаги — `docs/LAUNCH.md`).
- **Живой проект:** `<two-tier-dev>/bin/two-tier-upgrade <путь>` → ветка `kit-v3`: механика кита, ушедшие хуки и плагины сняты, прежние файлы — в архив с датой, раздутые PROGRESS и PLAN — в архив, отчёт `docs/upgrade-v3.md` (что осталось тимлиду, исполнителю и оператору). Проект кита v3.1 переходит тем же скриптом: `docs/GOAL.txt` → `docs/PROMPT.txt` отдельным коммитом «Тимлид: …». Push делает исполнитель проекта по своему стартовому запросу; merge — после приёмки.
