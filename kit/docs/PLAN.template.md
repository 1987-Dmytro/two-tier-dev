## Порядок

- Что диктуют `after:` и `[P]` спеки: <фича> перед <фича>. `[P]` безопасна, только если множества записи параллельных фич не пересекаются — выписать эти множества; пересеклись → последовательно.
- Чего SPEC не говорит: фича, которая читает файл, который другая двигает или переписывает, идёт до неё. Фактический `after:` записать здесь как отклонение от SPEC.
- Коммиты: один на фичу, сообщение `F<n>: …`, всегда `git add <точные пути>` — никогда `-a`, `-A`, `git add .`: в дереве бывает постороннее.

## Доказательство

Все чеки — из корня репо; один раз перед первым: `mkdir -p docs/evidence`. Идиом захвата, одинаковый для всех:
```bash
( set -o pipefail; { <КОМАНДА>; } 2>&1 | tee <абсолютный путь>/docs/evidence/F<n>-<check>-result.txt ); rc=$?
```

`tee` — вывод и в файл, и в транскрипт · `2>&1` **внутри** скобок — иначе диагностика (`bash -n`, `fatal:`, `No such file`) уйдёт мимо файла · `set -o pipefail` — статус чека, а не `tee` · `( … )` гасит `cd` и `exit` внутри чека и не пускает `pipefail` в остальную сессию · путь у `tee` **абсолютный** — иначе evidence уедет туда, куда чек сделал `cd`.

**F<n> — <фича>** → `docs/evidence/F<n>-<check>-result.txt`
- Команда чека из SPEC — verbatim: `<…>`.
- Исполняемая форма: блок, который реально исполняется; каждая правка против verbatim — с причиной, почему без неё чек не запускается или лжёт.
- Маркер: `<MARKER_OK>` последним `echo`. `tee` создаёт файл и для упавшего чека, поэтому доказательство — маркер в файле, а не существование файла.
- То, что «готово» требует, а чек не покрывает, — явным утверждением с пометкой «дополнение PLAN», в тот же файл evidence.
