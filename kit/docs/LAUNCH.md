# LAUNCH — строка запуска исполнителя, судьи заявлений и парный контрольный прогон

Кит v3.4 — **судья на заявлении**, а не на действии: «кусок готов» — коммит, его судят git-хуки кита и `abide check`; «фаза готова» — конец хода, его держит `spec-gate` по пунктам спеки; «плечо готово» — отчёт фазы и один круг `/verify-phase`. Между заявлениями модель-судья молчит.

## Запуск исполнителя
Строка запуска фазы — в `docs/PROCESS.md` проекта, раздел «Строка запуска исполнителя»; её пишет тимлид по таблице Environment. Из корня проекта; последний аргумент строки — стартовый запрос `"$(cat docs/PROMPT.txt)"` после `--` (шаблон `docs/PROMPT.template.txt`): фаза стартует без ручного набора — `claude "query"` открывает интерактивную сессию со стартовым запросом (cli-reference).

**Предохранитель окна — `bin/check-window && ` в начале строки** (F5). Один ход `claude -p` на `claude-haiku-5-5` (подписка: `env -u ANTHROPIC_API_KEY`) читает событие `rate_limit_event`: `unifiedWindows.seven_day.utilization` — доля от 0 до 1, её × 100 сравнивается с порогом `budgets.json` проекта. Окно 5 ч тариф отменил (слово оператора 06.11): предохранитель его не судит. Поле не документировано — единственное исключение из C2 (журнал intent 10.10); документированный `rate_limits.*.used_percentage` приходит только статус-строке идущей сессии (statusline), его показывает мод `window-guard`.
- неделя выше `window_seven_day_pct` (в ките — 100 %, решение 398: окна без ограничений, чек печатает числа и не отказывает; проект ужесточает порог в `project` своего `budgets.json`) — отказ до старта сессии: печатаются число и время сброса, `claude` не запускается; ниже — `&&` пускает строку дальше;
- мод `window-guard` во вкладке Code судит ту же неделю; порог он читает один раз, на старте сессии: подставленный порог действует с новой сессии;
- `--repair` — прежний флаг плеча починки: его порог был у окна 5 ч, теперь без действия; `bin/verify-phase` проверяет окно так же перед клоном — в `claude -p` воркфлоу на лимите не ждёт сброса, а падает (workflows);
- числа не сняты (нет входа в аккаунт, нет события, нет поля `unifiedWindows`) — отказ с причиной; в поле нет ключа `seven_day` — `WINDOW_WARN seven_day=fehlt`, неделя не судится, строка идёт дальше (решение 396);
- `--override` — единственный обход любого отказа: флаг пишется в строке (`bin/check-window --override && …`) словом оператора, обход печатается вместе с числами.

Флаги строки:
- `--permission-mode auto` (D2): `defaultMode: "auto"` из `.claude/settings.json` не действует, флаг перекрывает настройки (permission-modes);
- `--model claude-opus-5-5` — полным id: алиас `opus` меняется сам (model-config);
- `--effort ultracode` — `xhigh` и ultracode на сессию: Claude сам планирует воркфлоу на каждую существенную задачу (workflows, model-config). Нужен Claude Code 2.1.203+ и модель с `xhigh`. В `system/init` ultracode не виден — его доказывает флаг в строке;
- `--settings .claude/launch.settings.json` — файл тимлида: `autoMode.environment` (доверенная инфраструктура: из настроек проекта `autoMode` не читается, из `--settings` — читается, auto-mode-config), `enabledPlugins` и `skillOverrides` по таблице Environment;
- `--strict-mcp-config --mcp-config '<json>'` — MCP ровно из строки: срезаются MCP пользователя и плагинов (замер тимлида 07.10);
- `ENABLE_CLAUDEAI_MCP_SERVERS=false` — коннекторы claude.ai не грузятся; кит выключает их и сам (`disableClaudeAiConnectors`), auto memory — тоже (`autoMemoryEnabled: false`);
- `--setting-sources project,local` (v3.2) — настройки, хуки, плагины и скиллы пользователя в сессию исполнителя не входят: его инструменты — из репо, launch settings и таблицы Environment (Agent SDK settingSources, cli-reference);
- `--no-chrome` — встроенный MCP `claude-in-chrome` (настоящий Chrome оператора) в сессии исполнителя выключен (cli-reference);
- `--add-dir /tmp/two-tier-v3/skills` — скиллы пользователя со строкой «да»: из каталога `--add-dir` скиллы грузятся источником `project` (skills, permissions); ещё — если фаза работает вне репо;
- `--` перед стартовым запросом — конец флагов: `--add-dir` и `--mcp-config` берут по нескольку значений, и без `--` запрос уходит к ним лишним каталогом — сессия стартует без запроса (замер 09.10: `claude -p --add-dir <каталог> "<запрос>"` — «Input must be provided», с `--` — ответ).

`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` в строке больше нет (v3.3): Claude Code с 2.1.287 её не читает (mods overview), а Compact Adviser, которому она была нужна, у исполнителя выключен.

Ключ Jev — `TYPESAFE_API_KEY` в окружении терминала, из которого идёт строка (не в репо, не в evidence, не в журналах); строку его длины печатать можно, значение — нельзя. Без ключа молчит только Jev-часть: `abide check` коммита — пропуск (коммит проходит, строка в журнале), Belay пропускает, ячейка Jev отчёта фазы — «молчит», `bin/jev` выходит с кодом 2; правила кода коммита и `spec-gate` решают и без ключа.

## Вкладка Code и CLI
Вкладка Code приложения и `claude` из PATH — два движка: `bin/check-versions` печатает `VERSIONS cli= app= github=`, CLI отстал от GitHub — `HARNESS_WARN cli-behind` и строка `claude update`; скрипты ничего не ставят. Приложение читает те же файлы настроек, но не флаги строки.
- Профиль — `.claude/settings.local.json`, копия `.claude/launch.settings.json`: `effortLevel: xhigh`, `ultracode`, `enabledPlugins`, `skillOverrides`, deny MCP. Копию кладёт оператор: `cp .claude/launch.settings.json .claude/settings.local.json` (файл вне git, в клоне его нет; `bin/two-tier-init` только печатает шаг: профиль на месте включает плагины каждого прогона фикстур, а CLI дописывает их в реестр плагинов пользователя). `bin/check-harness --desktop`: файла нет — `HARNESS_WARN tab-profile` и пункт строки `вкладка:`, не красный; иное по смыслу — F6.3 красный, `tab-profile` с именами ключей, без значений. Фазу стартует `/phase` мода `phase-start` на ветке из `docs/PROMPT.txt`, чужая ветка — отказ; `/phase resume` шлёт строку Resume открытого стопа, `/phase halt` пишет `AGENT_STOP`. Окно судит мод `window-guard`: неделя выше `window_seven_day_pct` — отказ вызова инструмента с числами и сбросом до `/window override`; подагент и `claude -p` не судятся. Выше порога исполнитель не запушит и STOP: снимает только `/window override`.
- `permissions.blockWritesOutsideWorkingDirectories: true` (`.claude/settings.json`, CLI ≥ 2.1.314): Write, Edit и NotebookEdit вне рабочих каталогов — отказ, поле названо в отказе. Во вкладке `--add-dir` нет, поэтому Write и Edit в `/tmp/two-tier-v3` отказаны: фикстуры и черновики там пишет Bash или скрипт. Bash поле не держит: запись шеллом вне репо судит правило рубрики `no-writes-outside-repo`. В `additionalDirectories` пользователя каталоги считаются рабочими: соседние проекты поле там не закрывает — `HARNESS_WARN write-block-wider additional=<n>` (только число) и пункт строки `вкладка:`. В строке терминала рабочие каталоги — репо и названные `--add-dir` (в шаблоне `/tmp/two-tier-v3/skills`): Write в остальное `/tmp/two-tier-v3` отказан и там. `EnterWorktree` и `ExitWorktree` с полем исчезают, агент `isolation: worktree` под `.claude/worktrees` работает.
- `CLAUDE_CODE_SUBAGENT_MODEL` действует через `--settings` и окружение процесса; из `.claude/settings.local.json` и `.claude/settings.json` не доходит (замер 2.1.319, не документировано) — `HARNESS_WARN subagent-model-local`; `CLAUDE_CODE_SUBAGENT_EFFORT` — источник только changelog 2.1.316. `autoMode` из профиля не читается (auto-mode-config): только `--settings` и настройки пользователя.
- `bin/check-harness --desktop` — версии, брошенные worktree, пара поля записи, `system/init` прокси `claude -p` с профилем как settings.local против таблицы Environment, deny `docs/STATUS.md` и правка `kit/CLAUDE.md`, `PermissionDenied`. Прокси — не вкладка: effort и ultracode самой вкладки, модель подагента, MCP приложения, живой `/window` — гейт оператора SPEC §5.
- `PermissionDenied` → `.claude/hooks/permission-denied.mjs`: журнал `denials.jsonl` в `docs/evidence/`, только счётчики (инструмент, класс правила, n); событие идёт на отказ auto mode, не на deny-правило.

## Коммит — судьи кода и `abide check`
`bin/two-tier-init` и `bin/two-tier-upgrade` ставят `git config core.hooksPath .githooks` (githooks): хуки git кита судят и коммит из подпроцесса.
- `.githooks/commit-msg` — сначала код, закрыт на отказ: `no-secret-values` (значение секрета из окружения или литерал вида ключа в добавленной строке любого файла и в сообщении), `evidence-anonymized` (почта, кроме `noreply@` соавтора, или домашний путь в `docs/evidence/` и в сообщении), `team-lead-files` (файл списка `owner` без «Тимлид:»), `no-delete` (удаление — только `git mv` в `docs/archive/`); отказ называет правило и файл, а не найденный текст.
- Затем `abide check --json --phase edit --diff <staged patch>` по рубрике тимлида `.abide/rubric.json`, до 30 с: от 0,8 — отказ один раз, с правилом и файлом; тот же дифф ещё раз проходит как «rejected» — последнее слово за исполнителем, отклонённое читает тимлид; 0,5–0,8 — заметка; ошибка, таймаут, нет ключа — пропуск.
- `.githooks/pre-push` — `no-force-push`: push, который переписывает ветку удалённого репо (не fast-forward), — отказ при любом написании (`--force`, `+ветка`, `git -C`); новая ветка и fast-forward проходят.
- `.githooks/post-commit` — граф кода Graphify: есть `graphify-out/graph.json` и CLI `graphify` — `graphify update .` в фоне (AST, без модели и сети, пишет только в `graphify-out/`); коммит не ждёт и не падает. `core.hooksPath` глушит `.git/hooks`, поэтому `graphify hook install` при ките молчит: отчёт апгрейда называет такие хуки. После сборки — отметка `graphify-out/.built-head` (sha HEAD): граф не для HEAD — `HARNESS_WARN graph-age` в `bin/check-harness` (раздел `graph`). Ребейз запускает сборку на каждый коммит: graphify сериализует их, лишняя работа, не порча.
- Закрытый модуль: `frozen.json` и правило `frozen-paths` в `commit-msg` (в CI — `bin/check-frozen-diff`): коммит в замороженный путь без `offen` текущей SPEC — отказ с файлом, дифф больше `diff_cap` — отказ с числом, «Тимлид:» в код модуля — тоже отказ.
- Каждое решение — строка журнала `commit-judge.jsonl` в `docs/evidence/` (решение, судья, правило, файлы, оценка, хеш диффа — без сообщения и содержимого). Хуков Abide на правку и ход у исполнителя нет.

## Конец хода — `spec-gate`
Stop-хук кита `.claude/hooks/spec-gate.mjs` держит конец хода кодом по **пунктам** SPEC фазы — строкам `F<n>.<k>` под строкой фичи: у каждого пункта — строка `F<n>.<k> <сырой вывод пробы>` в `docs/evidence/F<n>-*-result.txt`, у фичи — её маркер отдельной строкой; ветка запушена; голова `docs/PROGRESS.md` (раздел «## Голова») называет сделанное, следующий шаг оператора и срок и переписана в этой сессии (сессия без коммитов кода на уже закрытой фазе — в этой фазе); `VERDICT: PASS` полного круга `/verify-phase` для HEAD и точечный PASS (`FEATURES: F<n>`) по каждой фиче, изменённой после него. Evidence начинается строкой `spec: SPEC-<n>` (пишет `bin/evidence`); файл другой SPEC не засчитывается. Комплект судится по запушенному HEAD: стартовый запрос, SPEC фазы, PROGRESS, evidence фич и файлы вердикта читаются из HEAD, и любой из них, который `git status` называет изменённым, неотслеживаемым или удалённым, держит ход по имени (журналы `spec-gate.jsonl`, `commit-judge.jsonl`, `jev.jsonl` и отчёт фазы — не комплект). Полный комплект — `SPEC_GATE_OK`, ход кончается; новая строка `STOP: <id>` с причиной SPEC §4, вопросом и resume-строкой в трёх строках под ней — тоже, один раз, и только из запушенного HEAD; иначе ход продолжается, блок называет id недостающего пункта. Jev хук не спрашивает.
- Режимы: `SPEC_GATE=off · shadow · active` в окружении, иначе `mode` в `.claude/spec-gate.json` (капы и вопрос ячейки Jev — файл тимлида). `off` — молчит; `shadow` — только строка журнала; `active` — блок. `claude -p` приёмки и пар `check-harness` идут с `SPEC_GATE=off`.
- Фоновые задачи — по `background_tasks[].type`: `monitor`, `workflow`, `shell` разбудят сессию — `pass background:<тип>`; `subagent`, `MCP task`, `teammate`, `cloud session` и задача без типа — суд комплекта. Вечный процесс в фоне (`tail -f`, dev-сервер) отпускает ход без суда: срока задачи во входе нет.
- Предохранители: один список три раза подряд — пропуск `no-progress`, `AGENT_STOP` — пропуск. Своего потолка блоков и часов нет: платформа сама кончает ход после 8 продолжений подряд (hooks), журнал несёт `platform_cap=8`. Причин стопа пять, пятая — `STOP-TL`, плечо построено. Каждое решение — строка журнала `spec-gate.jsonl` в `docs/evidence/` проекта; пропуск с причиной — строка отчёта фазы.

## Плечо — отчёт фазы и один круг приёмки
- `bin/phase-report` собирает кодом `phase-report.md` в `docs/evidence/`: матрица «пункт × коммиты, проба, наблюдение», списки «пункты без коммитов», «коммиты без пункта», «пункты без пробы», счёт судей коммита, пропуски хука и статус ячейки Jev — «подтверждает / противоречит / молчит», в тени: ответ, ошибка и таймаут Jev ход не меняют.
- Приёмка — один круг: `bin/verify-phase` из свежего клона запушенного HEAD проверяет все фичи; после починки — `bin/verify-phase F2 …` только по затронутым фичам (вердикт с строкой `FEATURES: F2`), второго полного круга нет. Выжившая мутация и пункт, не подтверждённый собственной командой проверяющего и её сырым выводом, — блокирующие.
- Глубина круга — метка фичи `risk: high|low` в конце её строки: `high` — полная глубина и ≥ 2 мутанта, `low` — свежий чек и пункты, без метки — один мутант; деплой на линию без `high` — `BUDGET_FAIL risk-tier`. Прошлый вердикт фичи идёт в круг объектом `{features, prior, risk}`, повторная находка помечается «повтор», вторая строка вердикта — классы дефектов и счёт. Сила проверяющего — `docs/evals/` репо кита (`EVAL_OK`, гоняет его `bin/check-verify`).
- `bin/verify-phase` дописывает строку счётчиков в `docs/evidence/verify-runs.jsonl` (K78: версия, секунды, команды в фоне); лимит 1800 с (поле `limit` строки) судит `bin/check-kit paar` по числам, только строки `status: completed`; `VERIFY_TIMEOUT` — счётчик. Файл меняется каждым прогоном: коммит вместе с вердиктом.
- Гейт кита `bin/gate-v3.4` (только репо кита; у проекта — свой `bin/gate-<n>`) — проект из `bin/two-tier-init` и копия клона telefon после `bin/two-tier-upgrade --branch kit-v3.4`: маркеры F1–F7, v3.3 и v3.2, строка на пункт F8; без ветки — `GATE_SKIP`; из разрешённых `offen` — только `F5.3`. Гейт идёт и внутри `bin/verify-phase` (в его лимите).

## Планки, замок, окно деплоя
- Линты спеки — `bin/check-budget --lints`: `planka-source` (планка без `docs/evidence/<файл>`, n, p50/p95 и без «ранняя» — `BUDGET_FAIL` до выдачи; звено вендора — слово «вендор» в звене или слово `vendor_words` из `checks/planken.json` в звене и инструменте — ещё `pair`), `scope-growth` (новая фича без «Поправка <решение>: слово оператора <дата>»), `planken-inline` (числа коридора в SPEC при ключе `planken:<ключ>`), `bin/gate-test` (`flaky` в `checks/planken.json` — решение тимлида).
- Пара одного часа — `checks/paired_stand.sh`: база и новый код попеременно ×2, правило печатается до прогона, `PAIR_OK|PAIR_FAIL diff_p50 diff_p95`; пороги — `pair` в `checks/planken.json`.
- Деплой — `scripts/deploy.template.sh`: паспорт модуля (`bin/check-passport`, `docs/MODUL.template.md`), шаг `regress` (`DEPLOY_OK` только после `REGRESS_OK`), строка `rollback: make rollback SHA=<prev>`. Окно деплоя — `bin/check-fenster`: `DEPLOY_OK` на линию без `LIVE_OK` или `ROLLBACK_OK` после него — красное; `bin/check-live` судит живой звонок по журналу. Канарейка раз в день — `scripts/canary.template.py`, `deploy/canary.timer`: письмо `OK|GELB|ROT`, итог ≤ 60 с; красное — инцидент.

## Слой Jev в харнесе кита
У исполнителя фаза — один ход, его заявления — коммит и конец хода. Toolgate, хуки Abide на правку и ход, Compact Adviser и Steer-or-Queue у исполнителя выключены — их события (каждое действие, сообщение человека посреди хода, совет человеку у терминала) есть только в сессиях оператора; их прежние файлы — в `docs/archive/` two-tier-dev (`kit-v3.2/claude-config/`). Хук на действие (PreToolUse, PostToolUse, UserPromptSubmit), который ходит в сеть или зовёт модель, — красный в `bin/check-harness`. Остаются: Jev Belay — тень (только журнал); мод `handoff` — хендофф и свежий контекст на 70 % окна; `bin/jev` — типизированные вопросы Jev; плагины слоя — `enabledPlugins` и `pluginConfigs` launch settings по таблице Environment, пины моделей — `env` launch settings.

Харнес кита — `.claude/settings.json`: `worktree.baseRef: "head"` (worktree агента воркфлоу ветвится от HEAD, а не от ветки по умолчанию), `workflowSizeGuideline: "medium"` (<10 агентов — совет модели, не потолок), узкие `permissions.allow` на `bin/check-*`, `bin/gate-*`, `make ci`.

## Контрольный прогон — парный
`bin/check-harness` берёт строку из `docs/PROCESS.md` (нет его — из шаблона кита) и гоняет её часть после `bin/check-window && ` как есть с `-p` на копии харнеса — свой каталог на запуск во `/tmp/two-tier-v3`:
`env -u ANTHROPIC_API_KEY` (только подписка), `--max-turns 3`, `--output-format stream-json --verbose`, без `--bare` (он пропускает хуки).
- run1 — заметка в `STEER.md` с маркером: маркер оказывается в файле-пробе;
- run2 — с `AGENT_STOP`: пробы нет, прогон остановлен на первом вызове, в выводе причина kill-switch;
- allow — под `dontAsk`, правила `permissions.allow` кита — через `--allowedTools`: в `-p` папка не доверена, и правила из `.claude/settings.json` не действуют (permissions, «What runs before you trust a folder»), в интерактивной сессии — после диалога доверия. `bin/check-*` идёт, команда вне правил — отказ;
- плюс: в `system/init` режим `auto` и `apiKeySource none`; поля settings по SPEC; `claude doctor` без ошибок настроек.
- копия харнеса несёт свой CLAUDE.md, где оператор авторизует пробы. Правила кита («`git add` по точным путям») агент воркфлоу ставит выше промпта скрипта и иначе сам не пробует то, что должен отказать хук.

Гонять при смене модели, релизе Claude Code и правке харнеса или таблицы; итог «до и после» — строкой в CHANGELOG кита.
