# The standing prompt — the operator pastes THIS, verbatim, into a fresh executor session, every time

```
Phase <phase-name>. Read, in this order and nothing else first: git log -15 --oneline; docs/plans/<phase-name>.PROGRESS.md; the NEWEST dated section of docs/reviews/<date>-plan-<phase-name>.md; docs/PHASE-<phase-name>.md §8 as the DONE list. Commit any modified team-lead file by path first. Then do exactly ONE item: the "next" line of PROGRESS. Verify it with its own check and show the output. Commit by path. Update PROGRESS (done / next / open stop, ≤60 lines). If you reach a stop-point — a paid or irreversible step not yet authorised, a design fork the plan does not settle, a test that would have to be weakened, a sealed file that would move — write it into PROGRESS as the open stop (≤15 lines: class, stop-point, question, tree state) and END YOUR TURN. Never add a test, pin, guard or ledger the phase file did not ask for; name the need in PROGRESS instead. Money: the step's cap is in its registration record; the platform's hard stop is derived from it; one ledger reading per session.
```

## What the team lead sends WITH the prompt, every time (≤5 lines)
What the item is · why now · what changes on disk · the risk (money: the cap and the line) · the check the
executor must show. The operator's action is always one of two: paste the prompt, or answer a decision table.

## What comes back
The executor's PROGRESS (done / next / open stop) and the operator's word «done, check it». Acceptance
follows the skill's §6: diff, artifact, the team lead's own re-run of the check, numbers from result files,
a fresh verifier for money — then a tick, one decision line, STATUS with a finish date.
